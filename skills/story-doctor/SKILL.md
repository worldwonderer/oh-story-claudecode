# story-doctor：部署与项目体检

**治的病**：能力检测散落在写作途中。agent 能不能 spawn、外包 CLI 在不在、追踪结构完不完整，过去都是写到一半才发现——用户已经投入了一章的时间，才知道自己一直在降级模式里跑。本 skill 把这些检查集中到一次显式调用，让用户**开写之前**就知道会拿到什么、拿不到什么。

## 何时运行

- **story-setup 部署完成后**自动跑一次，把结果并进安装报告。
- **用户主动要求**时（`/story-doctor`、「检查一下环境」「为什么回落 solo」）。
- **写作流程发现异常**时提示用户跑，例如 agent spawn 失败、外包不可用、追踪校验失败——只提示，不要自己在写作中途跑一遍完整体检。

**不要挂进 session-start。** 那个 hook 的原则是「无信息时完全静默」，而完整体检包含联网检查（最坏 20 秒）。每次开会话都付这个代价不值得。session-start 只做瞬时判断（例如 `command -v agy`），发现问题就建议跑 `/story-doctor`。

## 怎么跑

```
for PYBIN in python3 python py; do "$PYBIN" -c "" 2>/dev/null && break; done
"$PYBIN" "{story-doctor skill目录}/scripts/story_doctor.py" --project {项目根}
```

**不要裸调 `python3`**：Windows 上没有 `python3` 时会 exit 49，体检直接失败——按跨平台约定先探测解释器。

脚本**只依赖标准库、完全自包含**，不 import 任何 skill 内模块——doctor 要诊断的正是「部署坏了」，如果它自己依赖那份部署，坏的时候就一起哑了。所以部署残缺时它照样能跑。

常用参数：

| 参数 | 用途 |
|---|---|
| `--json` | 机器可读输出，用于把结果并进其他报告 |
| `--fix` | 只应用 **auto** 层修复；`prompt` / `refuse` 层一律不动 |
| `--fix --dry-run` | 只列出会修什么，一个字节都不写。**不确定时先跑这个给用户看** |
| `--check-delegate` | 额外跑联网的外包鉴权检查（约 5-20 秒），默认不跑 |
| `--only <id>` / `--skip <id>` | 按 checkId 过滤 |
| `--package <路径>` | 显式指定源 skill 包根；默认从脚本位置推断 |

**关于 `--package`**：doctor 平时是从项目内那份部署（`.claude/skills/story-doctor/`）跑起来的，此时推断出的包根就是项目自己——「修复源」和「待修目标」是同一棵树。缺的 skill 在源里同样缺，**`--fix` 修不了自己**。脚本会识别这种情况，把它报成需确认而不是谎称能自动修，并指出两条出路：重跑 `/story-setup`（它知道源包在哪），或 `--package` 指向源包。**不要把这种情况说成「skill 包损坏」**——包没坏，只是手上这份不能当源。

退出码：`0` 全绿 · `1` 有 warning · `2` 有 error · `3` 用法错误。

## 三档严重度，报告必须区分

| 档 | 含义 | 对用户的话术 |
|---|---|---|
| `error` | 写作**会失败** | 先处理再开写 |
| `warning` | 能写但**降级** | 明确说清「你会拿到什么、拿不到什么」 |
| `info` | 纯信息 | 不要渲染成问题 |

**`warning` 这一档最重要**：agent 缺失会回落 solo（单视角，失去多 agent 协作）、Node 缺失会停用正文兜底网、外包不可用会回落本地写手。这些都能写，但用户拿到的东西和他以为的不一样——不要笼统说「有几个警告」，要逐条说清降级后果。

## 三层修复，边界取自文件所有权

修复分层直接对应 `story-setup/UPGRADING.md` 的「文件所有权」，**不要另造一套**：

| 层 | 对应所有权 | 行为 |
|---|---|---|
| `auto` | story-setup 管理，可替换 | `--fix` 直接从 skill 包重铺，不问 |
| `prompt` | 用户与 story-setup 共同维护 | **必须先用 AskUserQuestion 说明影响再动**，通常是引导重跑 /story-setup |
| `refuse` | 用户状态，不覆盖 | **永不自动改**，只给手动步骤 |

绝对边界：`{书名}/正文/`、`设定/`、`大纲/`、`追踪/`、`正文.md`、`.active-book` 属于用户状态。**doctor 在任何情况下都不写这些路径**，追踪结构损坏也只给迁移指引，不代劳。

`--fix` 只做 `auto` 层。看到 `prompt` 层的发现时，先把影响讲清楚（会覆盖哪些受管文件、用户自定义部分怎么保留），得到明确同意再执行对应动作；用户拒绝就如实报告「未修复」并继续，不要反复追问。

auto 层不做备份：它覆盖的是受管副本，源在 skill 包里、目标不含用户内容，备份没有信息量；真正要保护的正文/设定/追踪在 `refuse` 层，根本不会被碰。**用 `--dry-run` 代替备份**——先让用户看清要动哪些文件，再决定。

`--fix` 修完会**重跑全部检查**，报告的是修复后的真实状态，不是修之前的快照。如实转述这个结果，不要把「修了几项」说成「已恢复健康」——修完仍有 error 是可能的。

## 报告怎么写

1. 先给一句总判：能不能正常写作。
2. 再按 error → warning → info 顺序列出，每条带 checkId（用户报问题时可以直接引用）。
3. 每条给出**可执行的下一步**，不要只说「有问题」。
4. `--fix` 跑过就列出实际修了什么，以及修完还剩什么。
5. 不要把 `info` 渲染成问题，也不要为了让报告好看而省略 `warning`。

## 边界

- doctor **只诊断和修部署**，不碰稿子。任何涉及正文质量、字数、去 AI 味的问题都不在本 skill 范围内。
- 不要在写作流程中途插入完整体检——发现异常时提示用户跑，由用户决定何时中断。
- 检查项要与 story-setup 的部署契约保持一致。改了部署产物就要同步改这里的检查，`scripts/check-story-doctor.sh` 会验两边不漂移。
